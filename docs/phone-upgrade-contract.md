# 手机端升级与兼容契约

生效日期：2026-10-18。依据用户明确要求，将自定义改动和工具的升级保留、接口适配、验证与回退列为后续手机端升级的必做事项。

适用于 APK 覆盖升级、运行资源更新、DSH 核心/SDK 更新，以及影响已有工具、插件、技能或配置的变更。维护者负责在交付前完成适配并提供证据，不把每次手动修复留给使用者。

这是维护和验收要求。现有独立 MCP 迁移逻辑只覆盖已识别的服务目录；本契约不代表已经实现任意补丁的自动适配、所有目录的自动备份或整个升级的自动回退。后续升级必须按实际实现和结果逐项验收。

## 1. 升级前盘点实际环境

- 确认目标设备、包名、签名、应用版本、资源版本、实际 DSH/SDK 版本及当前任务状态。记录源码版本和已有未提交修改。
- 读取正式配置和服务状态，盘点全部已有 MCP、后装插件、用户技能、人设、账号凭据引用、配对及工作区。工具清单动态读取，不把某次设备上的数量写成固定基线。
- 区分随包程序、持久用户扩展、运行数据和外部运行时。为需保留的文件记录相对路径、大小和 SHA，配置另做语义核对。
- 检查显式文件入口、符号链接和私有 SDK 副本，确认当前真正加载的代码。不能仅凭仓库代码、下载目录 APK 或版本标签认定手机已使用新版。
- 在本次授权范围内准备可校验、可恢复的备份，记录包含和排除的目录。空间、依赖、迁移或恢复条件不满足时，不替换现有可用环境。

## 2. 用户扩展和数据必须保留

| 内容 | 保存及升级约束 |
| --- | --- |
| 独立 MCP | 完整服务及依赖放 `$DSH_HOME/extensions/<唯一名称>/`；运行数据放 `$DSH_HOME/storage/<唯一名称>/`。已有正确接入的目录不为统一命名无故搬动。 |
| 启动配置 | 优先使用 `node` 和以 `$DSH_HOME` 开头的参数、cwd；本应用 Node 与库目录在每次启动时解析为当前 APK，保留其他环境变量和外部运行时的原有含义。 |
| 外部 HTTP/SSE MCP | 保留地址、凭据引用和配置；连接验证区分服务离线、网络错误和协议不兼容，不把错误归为配置丢失或擅自更换账号。 |
| 后装插件 | 使用独立包名，保留依赖、组合包登记和启用状态；与新版内置包同名时先明确保留、改名隔离或定向迁移方案，不静默替换用户改动。 |
| 用户技能及附件 | 保留正文、配套文件、启用状态和工作区可见性；用户改动与随包技能顶层目录同名时同样处理冲突，不整包覆盖。 |
| 账号、会话及个人资料 | 保留凭据、聊天、附件、人设、记忆、学习记录、配对及工作区，不以清数据、重置 profile、禁用原有权限或移除功能完成升级。 |

不得将维护者手机的用户目录、真实密钥或私人配置打进发行资源。凭据继续保存在已有凭据库，证据仅记录必要的引用或私有文件哈希，不回显凭据值。

覆盖安装时保持相同应用身份和签名；卸载、清除数据、更换包名不属于覆盖升级，也不能用来完成本契约的保留验收。

## 3. 接口变化由维护源码适配

1. 对照旧版与目标版的 MCP 协商、工具定义、参数、结果、错误、取消、插件注册、依赖注入、RPC 和配置格式，只修改实际发生变化的连接部分。
2. 标准 MCP 仍兼容时保留原服务；需要转换时，在连接层明确新旧字段映射。保留工具名称、参数含义、结果及错误语义，不静默删参数、吞错误或放宽权限。
3. 插件入口、配置和依赖变化同时迁移，保留用户自定义项；迁移须可重复执行，不重复登记工具、不重复写入业务数据、不重放已完成的外部操作。
4. 核心、SDK、界面和原生代码补丁进入维护源码，记录适用版本及原文件校验；原版本不匹配时先重新适配，不把旧产物直接覆盖新版核心。不得依靠手机上临时改文件维持功能。
5. 对私有 SDK、显式文件入口及插件自带副本单独核查。需要继续使用的副本也完成适配，并验证实际入口；不能让旧副本遮蔽新版修复后仍宣称升级成功。

适配沿用现有会话权限、停止和取消语义、身份及凭据隔离，不自动新增权限、切换模型或调用付费服务。

## 4. 在副本上验证后再交付

验证使用真实升级前配置和扩展的私有副本；证据必须覆盖以下场景，并注明执行环境：

| 场景 | 必须核对的结果 |
| --- | --- |
| 正常升级 | 从旧版升级目标版后，原扩展及资料按清单保留；全部原启用项仍有登记，正式状态和工具发现符合基线；受影响工具完成至少一次无副作用的代表性调用。 |
| 相邻边界 | 按变更范围验证相对依赖、含空格/中文路径、旧 Node/库路径、同名包及技能冲突、共享存储工作区可见性、私有 SDK 入口和外部服务配置；未受影响项保持。 |
| 失败和恢复 | 实际制造相关迁移或连接失败，核对没有破坏旧文件、配置及可用入口，恢复后重新启动或重连成功；再次执行迁移不会重复副作用。 |

涉及 Android 启动、原生库或迁移器的变更，须在隔离 Android UID、测试设备或其他不触碰正式数据的环境完成真实旧版到新版的覆盖升级。Mac Node 副本和浏览器夹具不能替代 Android 覆盖安装与原生界面验收。

复用已有 [MCP 升级测试](../peer/mcp-manager/upgrade.test.mjs)、[Android MCP 升级验证入口](../scripts/test-android-mcp-upgrade.py) 和 [恢复验证入口](../scripts/test-android-recovery.py)，先确认它们适用于本次版本；脚本不适用时更新相关夹具或按同等标准验证，不能跳过后宣称通过。

普通文档、图标等未影响工具或迁移的变更按实际范围检查，无需为凑齐用例反复重跑无关测试。受影响工具的业务调用涉及付费或外部写入时，使用隔离夹具和无副作用用例，正式调用按当前用户授权执行。

## 5. 构建与部署检查

- 使用维护源码构建。资源变化增加 `NodeRunner.ASSET_VERSION`，仅图标等无运行资源变化的更新不强制重解压；应用版本和资源版本分别核对。
- 先完成资源生成与校验，再执行 clean APK 构建。核对源码补丁进入实际资源，包含 hydrate 后的两处运行副本、模块 exports、依赖闭包和手机真正执行的组合包登记；手机直接启用的模块不能只登记到桌面组合包。
- 核对 APK 签名、包名、版本、ABI、ZIP 完整性、资源及原生库。文件体积异常时核实引用压缩体积和孤立 ZIP 数据，不通过删除用户功能或资料缩包。
- 正式设备安装、重启和恢复按已有用户授权执行；存在运行中任务时保持服务，等待任务结束，不把本契约当作打断任务的授权。
- 部署前重新读取状态，防止用旧备份覆盖用户并发新增的配置、模型选择和会话。部署后核对已安装 APK、实际资源版本、实际加载代码、正式工具状态及受影响的界面入口。

## 6. 失败处理和回退

- 明确检查、备份、迁移、激活和验收的阶段。迁移未完成时保留原程序和连接配置；已经激活但验收失败时，使用本次可兼容的恢复方案回到可用版本，不将部分更新当作成功。
- 回退程序与配置时保留用户在此期间产生的新会话、凭据和业务数据；涉及数据格式变化时必须有经验证的兼容恢复方案，不能直接用旧 APK 读取已迁移数据来猜测兼容。
- 现有“服务 → 备份与恢复”是插件及运行环境恢复，不是 APK 降级，也不覆盖全部用户数据和外部 Termux 环境。具体范围、原生库兼容限制和恢复前保存见 [备份与恢复说明](phone-recovery.md)；不足以覆盖本次风险时先补齐方案。
- 回退后验证原工具发现与调用可恢复，并保留失败原因、文件校验和恢复结果。任何备份内容含私人配置时留在私有位置，不随公开报告、源码或 APK 分发。

## 7. 每次升级交付回执

在私有交付记录中写明：源码及补丁版本；旧/新应用、资源和 SDK 版本；保留清单及冲突处理；适配的接口和实际入口；测试环境、命令、结果及失败恢复证据；APK 大小、SHA、签名；设备部署状态和剩余待验收项。引用文件，不复制完整聊天或凭据。

必须分别说明“源码已改”“APK 已构建/复制”“已安装并加载”“工具发现通过”“代表性调用通过”。未安装或未实测就明确待验收，不宣称手机已修好、全部工具可用或以后永不失效。

本契约是持续维护规则；具体升级仍依据当轮任务范围和既有授权，不自动创建定时任务、安装应用、重启设备、发起推理或发布代码。
